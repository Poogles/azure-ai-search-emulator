# Phase 1 — Application Scaffold and End-to-End Test

## Purpose

Deliver a minimal but real end-to-end path: a runnable HTTP service in a Docker image, exercised by the official Python Azure AI Search SDK through testcontainers. This proves the compatibility boundary (SDK → HTTP → emulator) works before investing in the full API surface.

## Scope

### HTTP fixture capture (first task)

Before implementing any endpoints, capture the actual HTTP traffic generated by the Python SDK:

1. Write a small recording script in `source/tests/python/` that injects a custom `azure.core.pipeline.transport.HttpTransport` into the SDK clients, so every request/response pair is captured in-process (no external proxy, no extra tooling, fully deterministic).
2. Run the official `azure-search-documents` SDK (pinned version from `docs/decisions/`) through this recording transport.
3. Exercise: create index, upload 2 documents, search, delete index.
4. Record exact request lines, headers, query parameters, and response bodies.
5. Commit sanitized fixtures to `source/tests/python/fixtures/` (strip any dynamic IDs, timestamps, and `x-ms-client-request-id` values).
6. These fixtures are the source of truth for endpoint shapes in this phase and are replayed by the C# harness in Phase 3.

### Application scaffold (Rust)

- HTTP framework (Axum) with an application factory and configuration via environment variables:
  - `EMULATOR_PORT` (default `8080`)
  - `EMULATOR_STORAGE__MODE` (`memory` | `file`, default `memory`)
  - `EMULATOR_API_VERSIONS` (comma-separated, default `2024-07-01`)
  - `EMULATOR_LOG_LEVEL` (default `info`)
  - `EMULATOR_ENABLE_ADMIN` (default `true`)
- Minimal Azure-compatible endpoints, matching the captured fixtures:
  - `GET /health` → `200 {"status":"ok"}` (operational, not part of the Azure surface).
  - `PUT /indexes('{name}')?api-version=...` — create index with minimal schema validation.
  - `POST /indexes('{name}')/docs/index?api-version=...` — upload documents.
  - `POST /indexes('{name}')/docs/search?api-version=...` — search with basic full-text matching.
  - `DELETE /indexes('{name}')?api-version=...` — delete index.
  - `POST /admin/reset` — reset all state (gated by `EMULATOR_ENABLE_ADMIN`). Deliberately emulator-specific; it is not part of the Azure admin API surface that Phase 3 implements under `/admin/...`, and must not collide with those routes.
- In-memory storage implementation behind the `Storage` abstraction from the initial design, guarded by a read/write lock so concurrent requests cannot corrupt state. `EMULATOR_STORAGE__MODE=file` is not yet implemented in this phase; the application must fail fast at startup with a clear error rather than silently falling back to memory.
- Azure-compatible response shapes for the above operations (envelope, `@odata.count`, `@search.score`, etc.) as observed in the captured fixtures.
- Basic Azure-compatible error responses (404 index not found, 400 invalid request, 401 missing key) using the Azure error structure (`{"error":{"code":"...","message":"..."}}`).
- API version handling: accept and validate the `api-version` query parameter; reject unsupported versions explicitly with `400`.
- Authentication as a compatibility mechanism: accept any non-empty `api-key` header; missing or empty key returns `401` with Azure error structure.
- Structured logging of method, endpoint, API version, index, operation, and `x-ms-client-request-id` (if present). Request bodies are never logged.

### Search semantics (Phase 1)

Full-text matching for the e2e round trip, backed by **Tantivy** (see `docs/decisions/0003-search-engine.md`) rather than a hand-rolled matcher:

- Token-based full-text match across all `searchable: true` string fields, using Tantivy's default (English) analyzer.
- `search=*` or empty search term matches all documents.
- A multi-term search term matches a document when every whitespace-separated term matches at least one searchable field (AND semantics).
- Newly indexed documents are immediately searchable (the engine commits and reloads synchronously on every upload batch).
- Results ordered by key field (deterministic tie-break).
- `@search.score` set to `1.0` for all results (placeholder; real scoring in Phase 2).
- No boolean operators, no field-specific search, no filters (Phase 2).
- E2E search assertions must use whole-token search terms (terms that appear as complete tokens in the documents), so the same assertions would also pass against real Azure AI Search, whose matching is token-based.

### Containerisation

- Multi-stage `Dockerfile` at `source/rust/Dockerfile`: build with Rust toolchain, final stage is `distroless/static` or `scratch` (static binary, no runtime dependencies).
- Image built with `docker build -t aisearch-emulator source/rust` and runnable via `docker run`.
- `HEALTHCHECK` instruction. The final image has no shell or HTTP client, so the healthcheck is a hidden subcommand of the emulator binary itself (e.g. `aisearch-emulator healthcheck` performs `GET /health` against `EMULATOR_PORT` and exits non-zero on failure): `HEALTHCHECK CMD ["/aisearch-emulator", "healthcheck"]`.
- Image size target: < 20 MB.

### E2E tests (testcontainers, Python harness)

- E2E suite in `source/tests/python/tests/e2e/` using testcontainers-python to start the built Docker image.
- Tests use the **official `azure-search-documents` Python SDK** (`SearchClient`, `SearchIndexClient`) against the container — not raw HTTP.
- Minimum e2e scenarios:
  1. Container starts and passes healthcheck.
  2. Create an index via `SearchIndexClient.create_index`.
  3. Upload documents via `SearchClient.upload_documents`.
  4. Search via `SearchClient.search` and assert expected documents are returned.
  5. Delete the index via `SearchIndexClient.delete_index`; subsequent operations return Azure-compatible errors.
- Each test gets isolated state via `POST /admin/reset` between tests (fixture in `conftest.py`).

## Out of scope

- Full index/document/query API surface (Phase 2).
- Merge/merge-or-upload, filters, facets, pagination beyond basics (Phase 2).
- Persistent/file-backed storage (Phase 2).
- Full admin API surface (Phase 3; only `POST /admin/reset` is in scope here).
- C# SDK compatibility (Phase 3).

## Deliverables

1. Runnable application: `cargo run --manifest-path source/rust/Cargo.toml` serving on a configurable port (default `8080`).
2. Multi-stage `Dockerfile` at `source/rust/Dockerfile` and verified `docker build` / `docker run` (static binary, < 20 MB).
3. E2E test suite under `source/tests/python/tests/e2e/` using testcontainers + the Azure SDK.
4. Unit tests (inline `#[cfg(test)]`) for the minimal query matching and storage layer.
5. HTTP contract tests (Rust integration tests) covering the error paths the SDK cannot exercise: missing/empty `api-key` → `401`, unsupported `api-version` → `400`, operations on a deleted index → `404`.
6. HTTP fixtures committed to `source/tests/python/fixtures/` (sanitized request/response pairs).
7. README updated with local run, Docker run, and e2e test execution instructions.

## Checklist

- [ ] Fixtures committed to `source/tests/python/fixtures/` (sanitized, including `x-ms-client-request-id`).
- [ ] Endpoint routes and response shapes in the implementation match the captured fixtures.

### Application

- [ ] Application starts locally (`cargo run --manifest-path source/rust/Cargo.toml`) and serves `GET /health` with `200 {"status":"ok"}`.
- [ ] Configuration (port, storage mode, API version, log level, admin enable) is externalised via `EMULATOR_*` environment variables.
- [ ] `api-version` query parameter is captured; unsupported versions return `400` with a clear error.
- [ ] Any non-empty `api-key` header is accepted; missing/empty key returns `401` with Azure error structure.
- [ ] Index creation (`PUT /indexes('{name}')`) validates the schema and rejects unsupported field types explicitly.
- [ ] Document upload (`POST /indexes('{name}')/docs/index`) validates documents against the index schema.
- [ ] Search (`POST /indexes('{name}')/docs/search`) returns Azure-compatible response structure (`value`, `@search.score`, and `@odata.count` when `count=true`), matching the captured fixtures.
- [ ] Delete index (`DELETE /indexes('{name}')`) works; subsequent operations return `404`.
- [ ] `EMULATOR_STORAGE__MODE=file` fails fast at startup with a clear "not yet implemented" error.
- [ ] `POST /admin/reset` clears all state (gated by `EMULATOR_ENABLE_ADMIN`).
- [ ] Contract tests (Rust integration tests) cover the error paths the SDK cannot exercise: missing/empty `api-key` → `401`, unsupported `api-version` → `400`, operations on a deleted index → `404`.
- [ ] Errors use Azure-compatible error structure (`{"error":{"code":"...","message":"..."}}`).
- [ ] Logging records method, endpoint, API version, index, operation, and `x-ms-client-request-id`; request bodies are not logged.

### Container

- [ ] Multi-stage `Dockerfile` at `source/rust/Dockerfile` builds successfully (`docker build -t aisearch-emulator source/rust`).
- [ ] Final stage is `distroless/static` or `scratch` (no build tooling, no shell).

### E2E tests

- [ ] E2E tests use the official Python Azure SDK, not raw HTTP.
- [ ] Scenario: create index → upload documents → search returns expected documents.
- [ ] Scenario: deleting an index makes subsequent operations fail with Azure-compatible errors.
- [ ] Tests are isolated via `POST /admin/reset` between tests (conftest fixture) and deterministic.

- [ ] E2E suite runs in CI (with Docker available).

### Quality gates

## Exit criteria

A developer can build the Docker image (`docker build -t aisearch-emulator source/rust`), and the e2e suite (`source/tests/python/tests/e2e/`) proves that the official Python Azure AI Search SDK can create an index, upload documents, search, and delete the index against the containerised emulator with no application-level changes beyond endpoint configuration. HTTP fixtures are committed and match the implemented endpoints.
